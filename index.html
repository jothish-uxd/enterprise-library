Whole workflows, accessible by default.

A React library of enterprise patterns: data tables, filters, bulk actions, and multi-step forms, plus admin screens like audit logs and AI usage caps. Each one decides where focus goes, what a screen reader hears, and how every state looks, so your team stops solving it again on every screen.

$npm install enterprise-library

Coming soon. The package isn't published yet, and the name may change before release.

Live example

Four patterns working together: a filter bar, a sortable data table, bulk actions, and a details sheet. Choose a requester’s name to open the sheet; the table narrows to make room. Use only the keyboard, or turn on your screen reader. The strip under the example shows what gets announced.

  • Details sheet: moving focus in and out without trapping it.

Patterns, not parts

Most design systems stop at components: a checkbox, a button, a table cell. Most accessibility bugs show up in between, in how those parts behave together on a real screen. This library starts one level up.

  1. Layer 1TokensColor, type, spacing, and the focus ring.
  2. Layer 2ComponentsButton, Checkbox, Text field, Dialog. Bring your own or use ours.
  3. Layer 3 · this libraryPatternsData table, Bulk actions, Multi-step form, Command palette.
  4. Layer 4TemplatesReview queue, Settings page, Admin console.
What a component handles compared with what a pattern handles
ConcernA checkbox component handlesThe bulk actions pattern handles
KeyboardSpace toggles one box.Tab order across filters, select all, rows, and the action bar.
FocusShows a focus ring.Where focus goes after an action runs, a row disappears, or a dialog closes.
AnnouncementsIts own name and state.“3 requests approved,” result counts after filtering, sort changes.
StatesChecked, unchecked, disabled.Loading, no results, partial failure, no permission, undo.
ContentIts label.Button verbs, error wording, and confirmation copy.

Quick start

Describe your rows and columns, then name the filters and actions you need. Focus handling, announcements, and empty states come with the pattern.

AccessRequests.jsx
import { DataTable, FilterBar, BulkActions, DetailsSheet } from "enterprise-library";
import "enterprise-library/styles.css";

export function AccessRequests({ rows, onUpdate }) {
  return (
    <DataTable
      caption="Access requests"
      rows={rows}
      rowKey="id"
      itemName={{ one: "request", other: "requests" }}
      columns={[
        { key: "requester", header: "Requester", rowHeader: true, sortable: true },
        { key: "system", header: "System", priority: "low" },
        { key: "status", header: "Status", sortable: true },
        { key: "submitted", header: "Submitted", sortable: true },
      ]}
      filters={<FilterBar search={["requester", "system"]} facets={["status"]} />}
      bulkActions={
        <BulkActions
          actions={[
            { label: "Approve", verb: "Approved", run: ids => onUpdate(ids, "approved") },
            { label: "Deny", verb: "Denied", run: ids => onUpdate(ids, "denied") },
          ]}
        />
      }
      detail={row => <DetailsSheet label="Request details" title={row.requester} />}
    />
  );
}

What every pattern includes

A keyboard map
Every pattern documents its keys and follows the ARIA Authoring Practices, so it behaves the way people expect.
A focus plan
Each action has a set place for focus to land, including after deletes, dialogs, and route changes.
Written announcements
Status messages are part of the pattern, worded once and announced politely. Your screens stay quiet otherwise.
Every state designed
Loading, empty, no results, partial failure, and no permission all ship as part of the pattern.
HTML first
Real tables, buttons, and labels. ARIA only fills the gaps native elements leave.
Color means a message
Status and selection use shape, text, and weight. Color appears in one place only: red, yellow, and green messages for errors, warnings, and success, each with its own icon and words.
Light, dark, and high contrast
Surfaces follow your theme tokens, and Windows High Contrast gets system colors.
Content guidance
Recommended labels, verbs, and error messages for each pattern, written for the person using the screen.
Tests you can keep
Testing Library recipes that check names, roles, focus, and announcements in your own app.
Reduced motion
Transitions switch off when the operating system asks for less motion.

Pattern · Live

Data table

Records in rows, sortable by column. It’s a real <table>, so screen readers can move cell by cell and hear the column header and the row’s name with every value.

Keyboard

Keyboard support
TabMove between the column sort buttons.
Enter SpaceSort by the focused column. Press again to reverse.
Table keysMove cell by cell with your screen reader’s table commands, such as Ctrl+Alt+arrows in NVDA and JAWS.

Focus and announcements

  • Sorting keeps focus on the column button and announces the new order, such as “oldest first.”
  • The sorted header carries aria-sort, so screen readers say “sorted ascending.”
  • The requester column is a row header, so every value is read with that person’s name.
  • The caption names the table and shows how many rows it holds.
  • Status uses a shape and a word, never color alone.

Usage

RequestsTable.jsx
import { DataTable, Status } from "enterprise-library";

<DataTable
  caption="Access requests"
  rows={rows}
  rowKey="id"
  itemName={{ one: "request", other: "requests" }}
  defaultSort={{ key: "submitted", direction: "descending" }}
  columns={[
    { key: "requester", header: "Requester", rowHeader: true, sortable: true },
    { key: "system", header: "System", priority: "low" },
    { key: "status", header: "Status", sortable: true, render: row => <Status value={row.status} /> },
    { key: "submitted", header: "Submitted", sortable: true, type: "date",
      sortWords: { ascending: "oldest first", descending: "newest first" } },
  ]}
/>

Filter bar

Search and facet filters for a table or list. The results update as you type, and the new count is announced once you pause, so screen reader users aren’t interrupted on every key.

Keyboard

Keyboard support
TabSearch, then each status filter, then the table.
Space EnterTurn on the focused status filter.
EscIn search, clear the text.

Focus and announcements

  • Focus stays in search while the results update.
  • The count is announced 600 ms after you stop typing, not on every key.
  • Status filters are toggle buttons in a labeled group, and each one includes its count.
  • With no results, “clear all filters” resets everything and returns focus to search.

Usage

RequestFilters.jsx
import { FilterBar } from "enterprise-library";

<FilterBar
  itemName={{ one: "request", other: "requests" }}
  search={{ label: "Search", fields: ["requester", "system"], placeholder: "Requester or system" }}
  facets={[
    { key: "status", label: "Status", options: ["pending", "approved", "denied"], showCounts: true },
  ]}
  value={filters}
  onChange={setFilters}
/>

Props

FilterBar props
PropTypeDescription
search{ label, fields, placeholder }A labeled search field. The placeholder is a hint, never the label.
facetsFacet[]Groups of filter buttons. Each group gets a visible label.
valueFilterValueCurrent filters, for controlled use.
onChange(value) => voidCalled on every change.
announceDelaynumberMilliseconds to wait after typing before announcing the count. Default 600.
itemName{ one, other }Used in the count: “Showing 4 of 12 requests.”

Facet

Facet options
OptionTypeDescription
labelstringNames the group, such as “Status.”
optionsstring[]The values to filter by.
showCountsbooleanShows how many results each option would give. The count is part of the button’s name.
multiplebooleanAllow several options at once. Default false.

FilteredThe caption shows “4 of 12.”“Showing 4 of 12 requests.”
No resultsThe reason and a “clear all filters” button.“No requests match these filters.”

Hides selected rowsThose rows are unselected.“1 selected request was hidden and unselected.”

Pattern · Live

Bulk actions

Select several rows and act on them at once. Focus stays where you were, the result is announced in words, and every action can be undone or has to be confirmed.

Keyboard

Keyboard support
SpaceToggle the focused row, or select all from the header checkbox.
TabThe top action bar comes before the rows and the bottom one after them, so actions are one Tab away from either end.
EnterRun the focused action.

Focus and announcements

  • Both action bars show the same count and act on the same selection.
  • Each bar is a group named by its count, so entering one says “3 requests selected, group.”
  • Select all says how many rows it covers: “Select all 12 shown requests.”
  • After Approve or Deny, focus stays on the button and the result is announced with an Undo.
  • Actions stay focusable with nothing selected, and explain why they can’t run.
  • Undo disappears once used, so focus moves to Approve in the same bar.
  • Selected rows use a checkbox and a tint, never color alone.

Usage

RequestActions.jsx
import { BulkActions } from "enterprise-library";

<BulkActions
  itemName={{ one: "request", other: "requests" }}
  actions={[
    { label: "Approve", verb: "Approved", run: ids => approve(ids) },
    { label: "Deny", verb: "Denied", run: ids => deny(ids) },
    { label: "Delete", verb: "Deleted", run: ids => remove(ids),
      confirm: { title: count => `Delete ${count}?` } }, // can't be undone, so it asks first
  ]}
  undo
/>

Props

BulkActions props
PropTypeDescription
actionsBulkAction[]The buttons in the action bars, in order.
placement"both" | "top" | "bottom"Where the action bar appears. Default "both"; use one bar for short tables.
itemName{ one, other }Used in the count and results: “3 requests selected.”
undobooleanShow Undo after an action. Default true.
scope"shown" | "all"Whether select all covers only the rows shown or every page. The checkbox label says which.
onSelectionChange(ids) => voidCalled when the selection changes.

BulkAction

BulkAction options
OptionTypeDescription
labelstringThe button text: a verb, such as “Approve.”
verbstringPast tense for the result: “Approved 3 requests.”
run(ids) => PromiseDoes the work. Return failures to get a partial-failure message.
confirmConfirmOptionsRequired for actions that can’t be undone. Opens a destructive confirm.

States

Bulk actions states
StateWhat people seeWhat’s announced
Nothing selected“No requests selected”; actions look dimmed.On press: “Select at least one request to approve.”
RunningThe button reads “Approving…” and the bar is busy.“Approving 5 requests.”
DoneThe result and an Undo button.“Approved 5 requests.”
Partial failureThe result names what failed and why.“Approved 4 requests. 1 couldn’t be approved: Lando Calrissian needs a second approver.”

The example above shows the first and third states. Running and partial failure are part of the design but not in the example yet.

Pattern · Live

Details sheet

Choose a row and its details open in a sheet on the right. The table narrows to make room and stays usable, so people can compare records without losing their place.

Keyboard

Keyboard support
EnterOn a name, open its details. Focus moves to the sheet’s heading.
TabFrom the heading through Previous, Next, and the actions, then on to the rest of the page. Nothing is trapped.
EscClose the sheet and return to the name.

Focus and announcements

  • Opening moves focus to the heading. Closing returns it to the name you came from.
  • The sheet is a labeled region, not a dialog, so the table stays usable beside it.
  • Each name button says whether its sheet is expanded.
  • Previous and Next keep focus on the button and announce the new request.
  • The sheet never closes on its own. If a filter hides its row, it says so.
  • On wide screens the table hides columns the sheet already shows. On phones the sheet stacks below.

Usage

RequestDetails.jsx
import { DataTable, DetailsSheet } from "enterprise-library";

<DataTable
  caption="Access requests"
  rows={rows}
  rowKey="id"
  columns={columns}
  detail={row => (
    <DetailsSheet
      label="Request details"
      title={row.requester} // takes focus when the sheet opens
      actions={<ApproveDeny request={row} />}
    >
      <RequestFacts request={row} />
    </DetailsSheet>
  )}
/>

Props

DetailsSheet props
PropTypeDescription
labelstringNames the region, such as “Request details.”
titleReactNodeThe heading. It takes focus when the sheet opens.
open / onCloseboolean / () => voidFor controlled use. Inside DataTable, the table handles both.
position{ index, total }Shown as “3 of 12” between Previous and Next.
onPrevious / onNext() => voidMove through records without closing.
actionsReactNodeButtons in the sheet’s footer.
returnFocusRefObjectWhere focus goes on close. Defaults to the element that opened it.

States

Details sheet states
StateWhat people seeWhat’s announced
Loading detailsThe heading appears at once; the body is marked busy.“Loading details,” only after 1 second.
Row hidden by filtersA note under the status.Read with the sheet’s content.
Decision madeStatus and history update in the sheet and the table.“Approved Leia Organa’s request.”
Narrow screenThe sheet stacks under the table.Nothing; focus still moves to the heading.

Multi-step form

Long tasks, such as onboarding a vendor or setting up a system, split into short steps with clear progress, saved drafts, and one error summary per step.

Keyboard

Planned keyboard support
TabThrough the step’s fields, then Back and Continue.
EnterIn a text field, the same as Continue.
Step listCompleted steps are buttons, so you can go back to any of them.

Focus and announcements

Planned focus and announcements
WhenFocus goes toWhat’s announced
ContinueThe new step’s heading.“Step 2 of 4: Access details,” read from the heading.
Continue with errorsThe error summary at the top of the step.“2 problems on this step,” then each problem as a link to its field.
Choose an errorThe field with the problem.Its label, value, and error message.
Draft savedStays where it is.“Draft saved,” at most once a minute.
SubmitThe confirmation heading.“Request submitted. Reference AR-1053.”

  • Leaving with unsaved changes asks in the page, never in a browser pop-up.

Destructive confirm

A confirmation step for actions that can’t be undone. It names exactly what will be lost, starts on the safe choice, and puts focus somewhere sensible afterwards.

Keyboard

Planned keyboard support
TabBetween Cancel and the confirm button. Focus stays inside the dialog while it’s open.
EnterActivate the focused button.
EscCancel.

Focus and announcements

Planned focus and announcements
WhenFocus goes toWhat’s announced
OpensCancel.“Delete 3 access requests?, alert dialog,” then the body text.
Cancel or EscThe button that opened it.Nothing.
ConfirmWhere the deleted item was: the next row, the previous one, or the “No API keys left” message.“Deleted the Data vault key.”

Content

  • The title is a question that names the action and the count: “Delete 3 access requests?”
  • The body says what will be lost and that it can’t be undone.
  • The confirm button repeats the verb, such as “Delete requests,” never “OK” or “Yes.”
  • For high-risk deletes, typing the name turns the button on, and the field says why.
  • If the action can be undone, use Undo instead of a confirmation.

Pattern · Live

Notifications

Toasts for quick results and banners for problems that need attention. Each one is announced once, and none disappears before a slow reader is done with it.

Focus and announcements

Planned focus and announcements
WhenFocus goes toWhat’s announced
A toast appearsStays where it is.The message, politely, once.
A blocking errorStays where it is; a banner appears at the top of the page.The message, right away.
Dismiss a toastBack to where you were before you moved into it.Nothing.

Timing and limits

  • Toasts with a button, such as Undo, stay until dismissed.
  • Other toasts stay at least 6 seconds and pause while hovered or focused.
  • At most three show at once. The rest collapse into “2 more.”
  • Toasts sit in a labeled “Notifications” region, so screen reader users can jump to it.
  • A notification history keeps everything that was shown.

Pattern · Live

Empty, loading, error

Every region of an app has more states than its happy path. This pattern gives each one a heading, a plain reason, and a next step, and decides which ones are worth announcing.

States

Planned states and announcements
StateWhat people seeWhat’s announced
Loading, under 1 sNothing changes.Nothing.
Loading, over 1 sPlaceholder rows; the region is marked busy.“Loading access requests.”
LoadedThe content.“5 requests loaded,” only if loading was announced.
First use“No access requests yet” and how to create one.Nothing; it’s read when reached.
No results“No requests match these filters” and a way to clear them.The count, from the filter bar.
No permission“You don’t have access to this list” and who to ask.Nothing; it’s read when reached.
ErrorWhat failed, what to try, and Retry.“Couldn’t load access requests,” once.

Focus

  • Retry keeps focus on the button while it loads again.
  • A state never replaces the element that has focus without moving focus to the new state’s heading.
  • Placeholder rows are hidden from screen readers; the busy region speaks for them.

Audit log

A permanent record of who did what, and when. Filter by person, action, or result, and expand any event to see exactly what changed. Events can’t be edited or deleted.

Keyboard

Keyboard support
TabSearch, time range, result filters, the time sort, then each event’s details button.
Enter SpaceShow or hide an event’s details.
EscIn search, clear the text.

Focus and announcements

  • Each details button is named by its event, such as “Details for Changed AI usage cap, Oct 24, 09:42,” and says whether it’s expanded.
  • Details open in the row right below, so they’re next in reading order. Focus stays on the button.
  • The action column is the row header, so every value is read with what happened.
  • Results are “Allowed” or “Blocked” with a shape, and blocked events give the reason.
  • Changing filters announces the count once you pause.

Usage

AuditLog.jsx
import { AuditLog } from "enterprise-library/admin";

<AuditLog

  onExport={range => exportCsv(range)} // CSV with headers, same columns as the table
/>

AI usage and caps

How much of the organization’s monthly AI allowance each team has used, and the caps that limit it. Every number is written out, so the meters are never the only way to read them.

Keyboard

Keyboard support
EnterOn Edit cap, open the cap field. In the field, save.
EscCancel editing and return to Edit cap.
TabFrom the field to Save cap and Cancel.

Focus and announcements

  • Meters are hidden from screen readers; the used, cap, and percent cells say the same thing in words.
  • Status is “Under cap,” “Near cap,” or “At cap, paused,” each with its own shape.
  • Edit cap opens a labeled field in the row below and moves focus into it.
  • A cap below what’s already used asks for a second Save and says what will happen.
  • Saving returns focus to Edit cap and announces the new cap and percent.

Usage

import { UsageCaps } from "enterprise-library/admin";

<UsageCaps

  forecast // projects month-end use from the pace so far

/>

  • Scheduled emails put the summary in the email body, not only in an attachment.
  • Date ranges can be typed as well as picked from a calendar.
  • Long reports open with a list of their sections, linked to each heading.

Every device, license, and integration the organization owns, grouped by type, with owners and when each was last seen.

Configuration

Organization settings in sections, such as sign-in, data retention, and AI features. Every setting says who it affects, and every change is recorded in the audit log.

Focus and announcements

Planned focus and announcements
WhenFocus goes toWhat’s announced
Change a settingStays on the control; the section shows “Unsaved changes.”Nothing until you save.
Save a sectionStays on Save.“Sign-in settings saved. Logged in the audit log as EV-9033.”
A risky changeA destructive confirm.“Turn off required single sign-on for all 312 people?”

Content

  • On/off settings are switches that say “On” or “Off,” not only a knob position.
  • Each setting names who it affects: “All 312 people” or “Command team.”
  • Settings set above a team say “Inherited from organization,” with a link to where they’re set.
  • Each section saves on its own, so a mistake in one doesn’t block another. Discard puts the section back to its saved values.

Roles and permissions

Who can do what. Roles group permissions, and people get roles per team. The matrix is a real table, so it reads as “Editor, Approve access requests, checked” rather than a grid of dots.

Focus and announcements

Planned focus and announcements
WhenFocus goes toWhat’s announced
Change a permissionStays on the checkbox.“Editor, Approve access requests, checkbox, checked.”
Save a roleStays on Save.“Editor role saved. 48 people affected.”
Remove the last adminStays on the checkbox; a message appears beside it.“At least one admin is required.”

Content

  • Each role has a plain summary: “Editors can approve requests and run reports, but can’t change settings.”
  • Two roles can be compared side by side, with differences listed in words.
  • Saving a change lists how many people it affects before it applies.
